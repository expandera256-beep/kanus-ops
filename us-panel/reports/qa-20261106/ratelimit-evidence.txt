5) Hypothesis — why many login attempts produced no 429
==============================================================================
PROVEN:
- nginx DOES attach limit_req zone=uslic_account to location = /account/login
  (rate 5r/m, burst=2, nodelay). Not a “missing limit_req on /account/login” bug.
- Exact location match is present; not swallowed by ^~ /account/ without limits.
- Zone key is $binary_remote_addr (TCP peer), not XFF. No real_ip module in play.
- Access log shows nearly every QA hit from a DIFFERENT 140.248.50.x address
  (box egress rotation). Only 140.248.50.24 appears twice in-window, minutes apart.
- 429 count in-window = 0; responses are mostly 400 (app validation) plus one 200.

HYPOTHESIS (high confidence, consistent with proven facts):
- limit_req buckets are per connecting IP. Rotating box egress ⇒ each attempt
  lands in a fresh (or nearly fresh) bucket ⇒ burst/rate never exhausted ⇒ no 429.
- Even same-IP: 5r/m + burst 2 allows several quick requests before 429; sparse
  duplicates would still often stay under the limit.

HYPOTHESIS (lower confidence / not proven here):
- Go app may also rate-limit (or not) on X-Real-IP; with X-Real-IP=$remote_addr
  it would see the same rotating peer IPs. Not inspected in binary/source this pass.
- If QA’s “32 attempts” used a single IP via a sticky path, absence of 429 would
  need another explanation — but the access log for this window contradicts
  single-IP; it shows many distinct 140.248.50.* peers.

NOT supported by evidence:
- “limit_req not applied to /account/login” — false (it is applied).
- “location ordering sends /account/login to unlimited ^~ /account/” — false
  (`=` exact takes precedence).
